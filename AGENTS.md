# AGENTS.md

Guidance for AI coding agents and contributors working on go-cbor.

## Project

go-cbor is a Go implementation of CBOR (RFC 8949) with encoders and decoders that convert between Go data models and CBOR, similar to `encoding/json`. The module is `github.com/cybergarage/go-cbor`.

The implementation follows RFC 8949, and code comments cite its section numbers, such as `// 3.4.5.2.` or `(RFC 8949 Section 4.2.1)`. Keep this convention when adding or changing behavior.

## Layout

| Path | Contents |
|---|---|
| `cbor/` | The library package |
| `cbor/encoder.go`, `cbor/encoder_indefinite.go` | `Encoder`, encode modes, indefinite-length encoding |
| `cbor/decoder.go` | `Decoder`, decode modes, validity checks, tags |
| `cbor/unmarshaler.go`, `cbor/marshaler.go` | `Unmarshal()`, `UnmarshalTo()`, `Marshal()` |
| `cbor/json.go` | Conversion between CBOR and JSON (RFC 8949 Section 6) |
| `cbor/config.go` | `Config` shared by `Encoder` and `Decoder` (encode/decode modes and limits) |
| `cbor/errors.go` | Sentinel errors and `newError*()` helpers |
| `cbor/tag.go`, `cbor/simple.go` | `Tag` and `SimpleValue` types |
| `cbortest/` | Tests of the public API (external test package) |
| `cbortest/fuzz_test.go` | Generated by `cbortest/fuzz_test.pl`; edit the generator and the generated file together |
| `doc/` | Documents and images; see `doc/img/tools/README.md` for the conversion tables |

## Build and test

Go version: see `go.mod` (CI uses Go 1.25).

```
make                                  # format, vet, lint, and test (what CI runs)
go test ./...                         # all tests
go test -race ./...                   # with the race detector
golangci-lint run cbor cbortest       # lint with .golangci.yaml
cd cbortest && ./fuzz                 # run each fuzz test briefly
```

- Keep `golangci-lint` at 0 issues; `.golangci.yaml` enables all linters except the listed ones.
- For decoder changes, also run ad hoc fuzzing of `Decoder::Decode()` (and a decode-encode round trip) to check that malformed input returns errors instead of panicking.

## Conventions

- Errors wrap the sentinel errors in `errors.go` (`ErrDecode`, `ErrEncode`, `ErrUnmarshal`, `ErrNotSupported`, `ErrJSON`, `ErrInvalidUTF8`) through the `newError*()` helpers, so that callers can use `errors.Is()`. Malformed or invalid input returns `ErrDecode`; truncated input returns `io.ErrUnexpectedEOF`; `io.EOF` is returned only at the beginning of a data item.
- Decoder:
  - Read arguments with `readArgument()`/`readLength()`, which check the shortest form in `DecodeModeCoreDeterministic` and reject lengths that overflow `int`.
  - Arrays, maps, and tags call `enterNested()`/`leaveNested()` to enforce `MaxNestedLevels`.
  - Validate tag content and return `ErrDecode` for invalid content (RFC 8949 Section 5.3.2).
- Encoder:
  - The public `Encode()` counts elements of indefinite-length items; internal recursion must call `encode()`.
  - Write arguments with `encodeArgument()`, which uses the shortest form. Respect `EncodeMode()`: `EncodeModeTypePreserving` keeps the widths of Go types.
- New options go into `Config` with getter/setter methods and defaults in `NewConfig()`.
- Behavior that is visible to users is documented in `README.md` and, for conversions, in `doc/conversion.md`.

## Tests

- Add tests to `cbortest/` using the public API. Prefer the test vectors in RFC 8949 Appendix A, and cover malformed, truncated, and invalid input as well as valid input.
- When a feature depends on `EncodeMode` or `DecodeMode`, test the relevant modes.

## Documentation images

The conversion tables in `doc/img` (`conv_table.ods` and the PNG files) are generated from the measured behavior. Do not edit the PNG files by hand; update the tools and run `./doc/img/tools/update.sh` as described in `doc/img/tools/README.md`.

## ChangeLog and releases

- Add entries to `ChangeLog.md` under `## Unreleased` at the top, in the style `- Added/Updated/Fixed Xxx::Method() to ...`. Put changes that break existing behavior under `### Breaking changes`, with how to restore the previous behavior when possible.
- Releases are made by the maintainer: rename `## Unreleased` to `## vX.Y.Z (YYYY-MM-DD)`, commit it as `Update ChangeLog.md for vX.Y.Z`, tag the commit, and create a GitHub release whose notes are the ChangeLog section.
- Pull requests are squash-merged; keep one topic per pull request.
